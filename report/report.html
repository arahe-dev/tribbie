Project Report

Compact latent visual policies and a vision-language programmer for camera-only mobile manipulation
Author Name  ·  Machine Vision  ·  Deliverables: paper, presentation, demo reel, this report

1. Goal

The assignment asked for a machine-vision research project with a paper, a presentation and a demo. The project asks how small a robot's visual representation can be: a policy sees the world only through two low-resolution RGB cameras, compresses what it sees into 16 numbers, and must turn those numbers into motor commands. A second question is whether a large vision-language model (Claude Opus 5.5) can sit on top of such a policy and program it from camera images.

Everything runs in NVIDIA Isaac Sim 5.1 on one workstation (RTX A2000, 12 GB). Physics is PhysX; grasps are friction only. All success numbers in this report are measured from simulator object poses, not from what the policy reports about itself.

Three roles

The system has three separate roles, and it is easy to blur them:

  • Teacher (scripted controller). Reads exact object poses from the simulator, demonstrates each task and labels the student's mistakes during DAgger. It only produces training data and never acts in a reported run.
  • Student (the 16-D latent policy). Learns to copy the teacher from the two camera images alone, without the poses. The trained student becomes the pick and drop skills.
  • Operator (Claude Opus through claude -p). Calls the trained skills, looks at the cameras, checks outcomes and retries. It never sees the teacher or the training data.

Teacher to student is imitation learning; student to operator is a function call. A fourth role sits outside the running system: the teacher, simulator and training code were written by the author with Claude Opus as a coding assistant. That is the same model as the operator, in a different job; see Section 8 for why that matters.

3. How the project developed

The final design is the result of several failed versions. The failures explain the design, so they are listed in order.

  1. End-to-end joint-space policy (failed). One policy for the whole pick-drive-drop task, predicting joint-angle changes. It learned the task structure but never completed a delivery on its own.
  2. Camera near-clip bug. Isaac cameras default to a near clipping plane of about one metre. The head camera could not see anything directly in front of the robot. Fixed by setting the clipping range on every camera.
  3. Brittle teacher labels. A 6 cm drift of the base made the teacher switch from "grasp" to "drive back to the table", so DAgger labels contradicted each other. The teacher was restructured so base correction and arm motion are labelled separately.
  4. Hovering above objects. The teacher demanded 1 cm alignment before descending; the student never achieved it and hovered. A descent funnel (allowed height shrinks with alignment error) fixed it.
  5. Action space. In joint space, the millimetre corrections needed for grasping are about as small as the network's own error. Switching to gripper velocity in the arm frame (with a fixed IK step) made them learnable.
  6. Corrupted images. Two simulator instances on one GPU return unfinished, sky-only frames (100 % and 54 % in a controlled test; 47 % in one DAgger round). Most early evaluations had silently fed the student blank images. Fixed by running one simulator at a time, re-rendering flat frames and filtering them from training.
  7. Rotation removed from the policy. The policy wandered and spun the base. Base heading and wrist angle became fixed controllers; the policy only translates.
  8. Skills and a VLM programmer. The task was split into goto, pick and drop, and Opus writes programs of them. Pick- and drive-focused DAgger rounds produced specialist checkpoints.
  9. Planner for driving. Learned goto worked with 20 % teacher help (34/36) but not alone (1/10), so the demos use a grid planner for driving, labelled on screen as not learned.

4.2 What the latent encodes

A linear head on the latent recovers the teacher's task phase on 92.5 % of held-out frames (mean of three seeds). Keypoints from the spatial-softmax layer fall on the target object, the fingertips and the table edge.

The latent is not a PCA of the pixels. PCA keeps the directions in which the images vary most, whatever causes them, such as lighting or background. The encoder here is trained jointly with the action and phase outputs, so its 16 numbers keep what is needed to act (where the object is relative to the fingers, whether it is held, which stage the task is in) and drop the rest.

4.4 Opus as verifier

Opus was asked where each of three objects was in 24 rendered scenes (72 objects). With table, bin and overview views it was right 83 % of the time; with the overview alone, 53 %. Nearly all errors were "not visible" answers for objects hidden by bin walls; only one answer named a wrong location. In the recorded programmer run Opus delivered the blue ball, retried the red cube, then stopped with a wrong conclusion; afterwards it turned out that its dedicated table and bin cameras had rendered black in that run. Note what Opus was not asked to discover: the prompt states where the table and bins are and gives the recipe pick → face → goto → drop. Opus chooses the objects, the order, when to check and when to retry. The robot also holds still while each call runs, which is why a two-object run takes minutes.

4.5 Latency

0.6 ms per forward pass and 1.5 ms per decision for six arms on an idle GPU; 6–15 ms inside the running simulator; about 10 s per Opus call.

4.6 Deployment test: Opus alone vs Opus with the 16-D skill

The questions above test pieces in isolation. A deployment asks something simpler: given a robot, cameras and an instruction, does the object get picked up, and how long does it take? We ran the same instruction (“pick up the <colour> object”, colour cycled over red, green and blue, object positions jittered by a seeded random generator) under two conditions that share everything else: the robot, the side camera and wrist camera images, the Opus model and the per-call time limit.

  • Opus alone. Each call returns a gripper displacement of at most 8 cm per axis plus open/close; a fixed IK layer executes it. This is the common “LLM as controller” setup with no learned low-level policy.
  • Opus + 16-D skill. Each call returns pick(colour) or done; the latent policy runs the grasp from pixels at 15 Hz (up to 20 s per attempt, three attempts).

Success is read from PhysX: the commanded object is between the fingers and at least 5 cm above the table. Times are wall-clock and include Opus thinking; the robot holds still during a call.

7. Honest limitations

  • Simulation only, with Isaac's holonomic base model rather than wheel friction.
  • Narrow distribution: one arena, three objects in nearly fixed slots.
  • Small evaluation sets (8–20 trials per closed-loop condition).
  • Driving in the final demos is a planner, not the learned policy.
  • The six-arm relay footage shows the scripted teacher; its learned policy was never retrained after the camera fixes.
  • Ablations are offline only.
  • The deployment test has six trials per condition, one task (single pick) and one simulator; it shows the size of the gap, not a precise rate.
  • Opus's prompt for the programmer gives the arena layout and the skill recipe; it does not discover them.

8. Scope and next step

Where this fits now. Fixed, structured settings such as factory stations, warehouses and lab automation: one cell, known parts, stable lighting. A new skill costs a few hours, almost all of it simulator time for demonstrations and DAgger rounds; fitting the network itself takes minutes. Decisions take 1.5 ms on a GPU and 7.5 ms on a CPU.

What the open world needs. Much more varied scenes and objects; learned navigation (the learned driving skill succeeded 1/10 times alone here); memory or a world model, since the policy only sees the current frame; transfer from simulation to real cameras and friction; and probably a larger latent (64-D already beat 16-D offline). The split between a slow reasoning layer and a fast learned layer should carry over; the lower layer grows.

One Opus instead of two. Today the engineer (Opus as a coding assistant, writing the teacher with the author) and the operator (Opus calling skills) are separate. Merging them gives a loop in which the model is told a new task in plain language, writes a privileged teacher for it in simulation, collects demonstrations, trains a 16-D student, checks it against physics ground truth and adds it to its own toolbox before operating with it. This project has every stage of that loop except the automatic one: writing working teachers took several iterations and human corrections, and three camera faults were only found by inspecting raw frames, so a merged system would need those checks built in and a human approving each new skill.

9. Reflection

The single most useful lesson was that the vision pipeline needs testing before the model does. Three different rendering problems (a clipping default, unfinished frames from concurrent renderers, and black cameras) each silently corrupted training or evaluation data, and each looked like a modelling failure until the raw frames were inspected. The second lesson is about scale: a 16-number policy can perform a reactive skill from pixels but cannot chain a long task on its own with this much data; splitting the work between a fast learned layer and a slow reasoning layer is what made complete deliveries possible.
